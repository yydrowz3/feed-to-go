## 所有阶段共同遵守的约束

- 业务代码位于 `apps/web/src`；`apps/web/_deprecated` 只读参考，不导入、不移动、不删除，不进入最终构建。
- 复用当前 package.json 和锁文件中的依赖，不安装 spark-md5，不升级依赖。确需新包时先向用户确认。
- Router 使用 TanStack Router；所有提交型表单使用 TanStack Form，校验使用现有 Zod；通知使用 Sonner，图标使用 Lucide。
- Query 保存服务端数据；Zustand 保存会话与确需共享的客户端状态；表单和组件局部状态各归其所有者。不得将同一服务端列表再复制到 Zustand。
- 样式只使用组件中的 Tailwind / daisyUI 类，固定 daisyUI `night` 主题。现有 `src/index.css` 仅保留框架导入与插件配置；不增加 CSS 文件、自定义 CSS 规则、CSS Modules、组件 `<style>` 或业务内联 style。
- 浏览器通过必填 `VITE_API_BASE` 直接访问后端；本地示例为 `http://localhost:8095`。不添加 `/api` 前缀、不配置 Vite 或部署环境的 API / 媒体代理。
- 当前 Go 后端是接口事实来源。前端修正旧 Vue 接口适配；本组文档不授权修改后端或部署上线。
- 不扩展头像/简介编辑、标签流、通知中心、SSE、私信轮询、历史消息分页、视频编辑删除或旧 FeedView 调试页。
- 保留现有用户修改，尤其是 `.gitignore`、依赖及 `.env.example`；不覆盖真实 `.env`，不在文档或日志记录 token、密码。
- 每个有前端实际改动的编号实施步骤，必须按 [前端实施约定](../apps/web/AGENTS.md) 更新应用版本，默认执行 `pnpm version:bump` 递增 patch；版本文件与本步实现一起提交，实施记录及反馈写明版本前后值。纯文档/验证步骤无前端实际改动时不升版；同一步反复检查不重复升版。应用版本从 `0.1.0` 起记录，不追溯修改既有历史。

## 逐步骤 Git 提交要求

这是执行每个子计划时的必做流程，用户已授权创建本地 commit，无需逐次再次确认；不执行 push 或部署上线。

- **步骤粒度**：每份子计划“实施步骤”下的每个编号三级标题（例如“### 1. 建立目录与运行入口”）作为一个提交单位。完成其代码、相关测试和实施记录后立即 commit，不能等整个子计划结束再合并提交。
- **执行顺序**：实现本步 → 运行与本步相关且当前已可执行的检查 → 有前端实际改动时更新一次应用版本 → 更新本步实施记录（包含版本变化）→ 检查变更及暂存范围 → 执行 git commit → 核对提交结果，再开始下一步。测试随对应实现步骤补充，不全部推迟到阶段最后；阶段末再执行文档要求的完整验收。
- **检查失败**：先修复本步引入的问题并重新检查，不将明确失败的实现标记完成。外部联调阻塞或尚未建立的后续检查要如实记录，不声称已经通过；完成的可独立验证改动可以提交，但阶段联调仍标为待完成。
- **只提交本步内容**：先检查 git status、工作区 diff 和暂存区 diff，只按路径或补丁暂存本步改动。保留用户原有工作区和暂存内容，不能用无差别 git add、reset 或清理操作把无关修改混入或移除。
- **纯验证步骤**：阶段 05 的审计、回归等步骤，即使没有代码修复，也要写入本步实际结果，再提交该实施记录；不创建空提交，不虚构代码变更。若步骤已由既有提交完整实现，记录并引用该提交，不重复制造相同改动。
- **提交信息**：每一步都必须生成并提交包含标题和非空正文的完整 commit message，严格遵循 [commit-conventions.md](commit-conventions.md)，不能只生成或提交标题。标题为 `<emoji> <type>(<scope>): <description>`，description 使用英文祈使句、首字母小写、无句号，标题建议不超过 72 个字符；type、Emoji 和 scope 与实际变更对应。正文说明变更原因、主要内容、影响及实际检查结果，建议按 Why / What / Impact 组织；破坏性变更按要求说明。
- **不写共同作者信息**：标题、正文和 trailers 均不出现 `Co-authored-by`、`Co authored by` 或任何大小写形式的共同作者声明；不附加自动生成的共同作者署名。使用当前仓库正常 Git 作者配置。
- **提交后核对**：查看最新提交的 hash、完整 message 和文件范围，确认无共同作者信息、无无关文件。若工具或 hook 自动附加该信息，修正本次自己刚创建的提交后再继续，不改写用户已有历史。
- **记录交付**：每步完成后在执行反馈中给出步骤编号、commit 短 hash，以及一个文本代码块中的完整 commit message（标题、空行和正文），内容须与实际提交一致；阶段实施记录列出步骤、修改摘要和检查结果。当前提交自身 hash 可在后续记录或阶段反馈列出，不为回填自身 hash 循环创建提交。
- **明确禁止 push**：所有提交仅保存在本地；不运行 git push，也不以创建远程 PR 等操作替代本地提交。提交遇到身份、hook 或 Git 错误时保留改动并报告原因，不跳过校验或自动进入下一步。

完整提交信息示例（按实际步骤填写标题和正文，不直接套用整个阶段名，不虚构检查结果）：

```text
✨ feat(web): add direct backend client

Why:
- Allow the React application to call the Go backend directly.

What:
- Add JSON and FormData requests with session-aware token refresh.
- Forward abort signals and preserve typed HTTP errors.

Impact:
- Share one API client across feature modules without adding a proxy.
- Verify refresh and cancellation with injected fetch tests.
```

## 阶段间共享契约

01 确定以下契约，后续阶段沿用；必要修正必须同步修改受影响文档及调用方。

| 契约       | 固定约定                                                                                                                                                          |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 请求客户端 | `createApiClient` 注入 base URL、fetch 和会话访问器；`postJson` / `postForm` 接收 `signal` 和 `auth: 'none' / 'optional' / 'required'`；返回解析结果或抛 ApiError |
| 会话       | 保留 localStorage 的 `access_token`、`refresh_token`；会话变化使用递增 sessionId 隔离，刷新 token 不等同于更换会话                                                |
| 缓存       | 统一 key 工厂，所有业务 key 带 sessionId 和 viewerId（匿名为 0），资源 ID、排序和 limit 作为后续维度；不把 token 放入 key                                         |
| 数据       | wire DTO 保留后端 snake_case；页面继续消费统一类型，关注列表内部统一命名 followings；需要转换时在 api 层完成                                                      |
| 身份       | JWT 只作 UI 身份解析，权限与 token 有效性以服务端结果为准；私有接口必须带 Bearer token                                                                            |
| 取消       | Query 的 AbortSignal 传到 fetch；上传单独持有 AbortController；旧会话及旧资源响应不得覆盖当前页面                                                                 |
| 反馈       | 字段错误在表单展示，页面读取失败展示可重试状态，动作结果用一次 Sonner；主动取消不弹错误通知                                                                       |
| 执行入口   | 命令均从 `apps/web` 运行：`pnpm test`、`pnpm build`、`pnpm lint`；01 建立 Node 内置测试脚本，不新增测试依赖                                                       |

## 外部条件与完成口径

- 后端已根据后续独立请求加入 CORS 中间件，通过 `WEB_URL` 配置前端 origin，默认 `http://localhost:5173`，见 [后端 CORS 配置](backend-cors.md)。真实浏览器联调前仍需配置实际 origin、启动后端，并验证 OPTIONS 及业务错误响应；不使用代理绕过。
- 准备一个已有账号、另一个可互动账号，以及可浏览、可评论的视频数据。没有数据时可完成空态验收，但不能据此声称互动闭环已通过。
- 发布联调需要后端 Redis、上传目录与静态文件服务可用。MQ 开启时，点赞和评论成功响应可能早于读取结果；不得把这种延迟伪装为前端同步完成。
- 无后端时可通过注入传输层的单元测试验证逻辑，但只记为“代码检查通过，真实联调待完成”。任一必要联调项未完成，都不能标记最终交付完成。
- 每阶段结束在该阶段文档末尾记录日期、实施结果、执行命令和结果、人工验证、外部阻塞、后续事项。不要预先勾选通过项。
