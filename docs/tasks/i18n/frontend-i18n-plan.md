# 前端 i18n 与配套错误码改造方案

计划日期：2026-10-24。方案已实施，前端交付版本为 `0.1.13`；执行结果见 [i18n 验收记录](frontend-i18n-verification.md)，后端兼容变更见 [错误码契约](api-error-codes.md)。

## 一、目标与已确定的行为

支持 **English、简体中文、日本語**，语言代码分别为 `en`、`zh-CN`、`ja`。覆盖现有前端全部功能，并同步规范当前前端所调用接口的错误码及 HTTP 状态码。

| 项目 | 确定方案 |
|---|---|
| 默认语言 | 英文；首次访问不根据浏览器语言自动切换 |
| 语言选择 | 全局顶部入口，桌面端、移动端、未登录用户均可使用 |
| 选项名称 | 固定显示 `English / 简体中文 / 日本語` |
| 偏好保存 | 使用独立的 localStorage 键 `feed-to-go.locale` |
| 恢复规则 | 已保存的有效偏好优先；缺失、非法或读取失败时使用英文 |
| 切换方式 | 即时更新界面，无需刷新页面 |
| 内容边界 | 翻译产品界面；用户名、视频标题、评论、私信等用户内容保留原文 |
| URL | 保持现有路由，不增加语言前缀或查询参数 |
| 后端范围 | 当前前端调用的账号、视频、信息流、点赞、评论、关注、私信接口及共用鉴权、限流 |
| 暂不包含 | 繁体中文、账号语言偏好同步、未使用接口及 SSE 专项改造 |

现有前端为 React 19、TypeScript、Vite，尚无 i18n。改造需要处理的不只是 JSX 文案，还包括校验规则、上传状态、错误对象、日期格式和 API 默认值。

## 二、前端实现

### 1. 引入统一的国际化模块

新增 `i18next` 与 `react-i18next`，分别采用已核实的 `26.5.10`、`17.1.7`，同步更新锁文件。语言资源随应用打包，首版不增加远程翻译加载或浏览器语言检测插件。[依赖信息](https://registry.npmjs.org/react-i18next/17.1.7)

国际化模块负责：

- 定义 `Locale = 'en' | 'zh-CN' | 'ja'`、语言选项与偏好存取。
- 创建 i18n 实例，配置支持语言及 `fallbackLng: 'en'`。
- 提供统一的 React 翻译 Hook、语言切换方法及格式化工具。
- 为测试提供可独立创建的实例，避免语言状态在用例之间泄漏。

英文作为资源基准，按 `common`、`navigation`、`account`、`feed`、`video`、`comments`、`social`、`messages`、`publish`、`errors`、`validation` 拆分命名空间。中文和日文遵循相同结构。[i18next 配置说明](https://www.i18next.com/overview/configuration-options)

在首次 React 渲染前完成语言恢复和初始化，再挂载 Provider。Provider 同时覆盖正常应用和配置错误页面，避免 API 配置异常时退回固定中文界面。

### 2. 统一翻译接口与文案规则

组件通过统一的 `useAppTranslation()` 获取翻译能力；内部调用 `useTranslation()`，订阅语言变化。[React 集成说明](https://react.i18next.com/latest/usetranslation-hook)

约束如下：

- 使用语义化键名，例如 `navigation.home`、`publish.stages.uploading`。
- 根据英文资源派生键名类型，由封装检查键名；不为本功能整体开启项目严格模式。
- 用完整句子和参数插值替代拼接，例如“清除视频”“清除封面”分别定义。
- 英文数量文案使用复数规则，覆盖 `0 / 1 / 多条`。
- 静态导航和上传阶段表只保存翻译键，在渲染时翻译。
- 不在模块加载、API 标准化或状态初始化时保存已翻译字符串。
- 插值继续由 React 转义，不使用 HTML 拼接展示用户输入。

三种语言的键、插值参数与复数形式通过资源检查测试保持一致；遗漏翻译时运行时回退英文，同时作为验收缺陷处理。

### 3. 全量替换现有界面文案

| 模块 | 修改内容 |
|---|---|
| 应用外壳 | 桌面与移动导航、搜索框、登录状态、跳转到内容、语言入口 |
| 公共组件 | 加载、空状态、错误状态、确认弹窗、关闭按钮、配置错误、404 |
| 账号 | 登录、注册、改密、改名、退出、个人主页、作品与喜欢列表 |
| 信息流与视频 | 推荐/关注/榜单、分页提示、播放控件、点赞、分享、复制结果 |
| 评论与关注 | 评论抽屉、发布/删除、粉丝与关注列表、计数和操作反馈 |
| 私信 | 联系人、会话、历史范围提示、发送状态、草稿保留提示 |
| 发布 | 字段、文件约束、预览、校验、上传阶段、进度、重试及结果未知提示 |
| 无障碍属性 | `aria-label`、`alt`、`title`、placeholder、动态状态说明 |

语言选择器放在顶部搜索区域旁，使用带可访问名称的原生选择控件。移动端允许顶部换行，搜索区域保持 `min-width: 0`，避免英文和日文挤压布局。

切换语言时只更新 i18n 状态，不按语言重新设置组件 `key`，不重建 Router、QueryClient 或业务运行时。保留当前路由、搜索条件、表单草稿、选中文件、上传进度与播放位置。

### 4. 校验、错误与缓存改造

**表单校验**

当前 Zod 规则直接保存中文提示，账号表单还通过“请输入 + 字段名”拼接文案。统一改为保存稳定的校验键及必要参数，由表单展示层翻译。

覆盖账号、改密、改名、评论、私信和发布校验。保留现有业务约束；已显示的校验错误在切换语言后立即更新，不要求用户重新提交，也不重建表单。

**前端业务错误**

引入独立于语言的 `AppError`，携带稳定错误标识、参数和原始原因。业务状态保存错误对象或消息描述，不保存最终展示字符串。

增加统一的错误展示转换，供页面、表单和 Toast 使用：

- 已知前端错误：按错误标识翻译。
- 后端错误：按 `ApiError.code` 翻译。
- 网络错误：显示当前语言的连接失败提示。
- 未知错误：显示当前语言的通用提示。
- 取消和会话失效导致的 `AbortError`：继续遵循现有取消逻辑。

Toast 通过统一的可翻译消息组件展示，使仍可见的提示也能随语言更新。保留上传“结果暂时无法确认”和私信“草稿已保留”等具体恢复指引。

**API 数据默认值**

当前标准化层将“匿名用户”“未命名视频”写入业务数据。改为保留空值，在展示层使用当前语言补全文案。

同步检查头像、搜索过滤、视频详情到信息流的数据转换和查询缓存，确保切换语言后不会读取缓存中的旧语言默认文案。

### 5. 日期、数字和页面元信息

- 静态 HTML 的 `lang` 改为 `en`；恢复偏好和切换后更新为当前语言。
- 保留应用标题 `Feed to Go`，本次不额外引入各路由标题系统。
- 日期统一使用显式 locale 的 `Intl.DateTimeFormat`，映射为 `en-US / zh-CN / ja-JP`。
- 保持用户设备时区，语言选择不改变时间含义。
- 处理无效日期，显示对应语言的“日期未知”。
- 计数与进度数值使用统一格式化工具；资源 ID、文件名和媒体 URL 保持原值。
- 视频播放时间继续使用统一的 `mm:ss` 表示。

## 三、后端错误契约与客户端兼容

### 1. 建立稳定错误响应

错误响应采用以下最小结构：

```json
{
  "code": "USERNAME_TAKEN",
  "error": "username already exists"
}
```

`code` 用于程序判断和前端翻译；`error` 保留可读英文描述，兼容仍读取该字段的客户端。成功响应结构保持原样；上传错误已有的 `missing`、`completed`、`total` 等附加字段继续保留。

新增共享错误码清单，记录错误码、HTTP 状态和英文兼容描述；通过小型脚本生成 Go 常量/元数据及 TypeScript 类型，提供检查生成结果是否过期的命令。三语翻译资源人工维护，测试校验映射完整性。

后端通过统一的响应方法输出错误。Service 和 Repository 使用类型化错误、哨兵错误及 `errors.Is/As` 分类，不通过匹配 `err.Error()` 的文字决定错误码。

### 2. 规范 HTTP 状态码

| HTTP | 错误码与场景 |
|---|---|
| 400 | `VALIDATION_FAILED`：请求解析、必填字段、游标或分片索引非法；`INVALID_CURRENT_PASSWORD`；`SELF_FOLLOW_NOT_ALLOWED`；`UNSUPPORTED_FILE_TYPE`；`UPLOAD_HASH_MISMATCH` |
| 401 | `AUTH_REQUIRED`、`INVALID_TOKEN`、`TOKEN_EXPIRED`、`TOKEN_REVOKED`、`INVALID_REFRESH_TOKEN`、登录的 `INVALID_CREDENTIALS` |
| 403 | `FORBIDDEN`：已登录但无权限，如删除他人评论或访问他人的上传会话 |
| 404 | `ACCOUNT_NOT_FOUND`、`VIDEO_NOT_FOUND`、`COMMENT_NOT_FOUND`、`UPLOAD_SESSION_NOT_FOUND` |
| 409 | `USERNAME_TAKEN`、`ALREADY_LIKED`、`ALREADY_FOLLOWED`、`NOT_FOLLOWING`、`UPLOAD_INCOMPLETE` |
| 413 | `FILE_TOO_LARGE` |
| 429 | `RATE_LIMITED` |
| 500 | `INTERNAL_ERROR`：数据库、文件操作或内部数据异常等未明确分类的故障 |
| 503 | `UPLOAD_SERVICE_UNAVAILABLE`：分片上传所需 Redis 未配置或不可用 |

具体处理要求：

- 注册和改名的用户名唯一性冲突均返回 `USERNAME_TAKEN`，数据库唯一约束负责并发兜底。
- 登录时账号不存在与密码错误统一返回 `INVALID_CREDENTIALS`。
- 改密凭据不匹配统一返回 `INVALID_CURRENT_PASSWORD`；内部故障仍返回 500。
- 区分上传会话不存在、Redis 故障和会话数据损坏，分别返回 404、503、500。
- 删除他人评论改为 403，避免客户端误判为登录失效。
- 内部异常保留在服务端日志，响应使用登记的英文描述。
- 不新增后端语言协商，也不要求客户端发送语言请求头。

### 3. 调整客户端错误解析和恢复策略

扩展 `ApiError`，增加可选 `code`，保留现有 `status`、`payload` 和构造方式兼容性。统一解析错误码，页面不再直接展示任意 `error.message`。

兼容规则：

- 已知错误码优先使用对应三语提示。
- 旧后端缺少错误码、返回未知错误码或非 JSON 错误时，按 HTTP 状态及当前操作显示通用提示。
- 原始错误内容保留用于诊断，不作为翻译依据。

状态码调整必须同步验证以下行为：

- 受保护请求的 401 继续使用现有单次刷新与重放机制。
- 登录、注册和改密请求保持 `auth: none`，不触发令牌刷新。
- 403 不刷新令牌、不清除有效登录状态。
- 400、404、409、413、429 不自动重试。
- 分片上传保留现有网络错误和 5xx 的有限重试。
- 合并及发布遇到网络错误、取消或 5xx 时，继续保留结果未知提示，避免重复发布。
- 点赞、关注的 409 按原有错误恢复流程重新读取状态，不自动重复执行操作。

## 四、测试与验收

### 1. 资源与基础逻辑

沿用 Node 内置测试，增加：

- 默认英文、三语恢复、非法偏好、Storage 读写失败。
- 三语键名完整性、空译文、插值参数及英文复数形式。
- 所有共享错误码均有前端映射和三语提示。
- 缺失译文的英文回退。
- 日期、数字、无效日期及用户内容原样保留。
- 错误码生成产物与清单一致。

现有依赖中文异常文本的业务测试，改为断言稳定错误标识、状态和恢复行为。

### 2. 后端契约测试

使用现有隔离测试方式、数据库替身及 miniredis，覆盖：

- 参数错误 400、凭据错误 401、权限错误 403。
- 资源缺失 404、业务冲突 409、文件超限 413、限流 429。
- 内部故障 500、上传服务不可用 503。
- 所有受改造分支均返回有效 `code` 和兼容 `error`。
- 用户名并发冲突、上传会话缺失与 Redis 故障的正确区分。
- 错误响应继续具有现有 CORS 行为。

### 3. 浏览器回归

调整现有浏览器回归脚本，消除默认中文假设。流程定位优先使用稳定的表单 ID、语义属性，必要时增加测试标识；语言测试单独断言实际译文。

验收场景：

- 无偏好首次进入英文；三语切换、刷新恢复、退出再登录后偏好保留。
- 访客与登录用户均能切换，配置错误页面也能正确恢复语言。
- 表单校验、弹窗、Toast、后端报错和上传阶段完整三语显示。
- 表单报错后切换语言，错误更新且输入保留。
- 视频播放、私信编辑和上传过程中切换语言，业务状态保留。
- 桌面 `1440×900`、移动 `390×844` 下三语无横向溢出，切换入口可用。
- 保留现有登录刷新、草稿恢复、上传检查点及资源释放回归。

前端执行 `pnpm test`、`pnpm build`、`pnpm lint`，并完成浏览器回归；后端执行 `go test ./...`。验收以执行结果为准，本方案不预设现有测试已通过。

## 五、实施顺序与交付

1. **错误契约先行**：建立共享清单、生成检查及后端统一错误响应，完成状态码分类和契约测试。
2. **接入 i18n 基础**：依赖、资源、偏好恢复、Provider、顶部切换及格式化工具。
3. **迁移全部展示逻辑**：页面、无障碍文案、校验、前端错误、Toast、数据默认值及日期。
4. **完成兼容与回归**：更新错误恢复测试、浏览器脚本，检查三语覆盖及移动布局。
5. **交付文档与版本**：更新 README、错误码说明和验收记录。按前端现有规则，一个完整实施单元只升版一次；若实施起点仍为 `0.1.12`，默认交付版本为 `0.1.13`。

如需分步部署，先部署后端错误契约，再部署前端；新前端同时兼容缺少错误码的旧响应。发布记录须明确 HTTP 状态码调整，不能仅标注为翻译更新。

实施前重新核对工作区：当前已存在其他后端改动，需在其基础上整合，保留已有修改。此次不需要数据库结构迁移，语言偏好独立于账号和登录令牌保存。
